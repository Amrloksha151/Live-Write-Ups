## Reconnaissance

The first thing I wanted to know was whether the application normalized encoded input before the firewall inspected it. If the firewall and backend disagreed on character handling, that would be the narrowest path to bypass.

```http
GET /search?q=%C3%A9 HTTP/1.1
Host: target.local
```

The response timing suggested the application reached the backend, but the WAF only reacted to a subset of payload shapes.

This mismatch was the key. The WAF was analyzing traffic at one layer, but the backend was normalizing at another.

## Exploitation Path

I started chaining lookalike characters with percent-encoding. The key was not the payload itself, but the mismatch in where the normalization occurred.

The breakthrough: Unicode provides multiple ways to represent the same character. If I sent the "wrong" representation, the WAF might pass it through, but the backend would normalize it back to the intended form.

<DecisionPoint
  question="Which payload family is most likely to expose a parser mismatch?"
  chosen="UTF-8 lookalikes wrapped in a benign query shape"
  reason="A low-noise probe made it easier to distinguish a blocked pattern from a rejected parameter format."
  alternatives={["Longer SQL payloads", "Binary content injection", "Header-based injection"]}
/>

```javascript
const probe = '/search?q=' + encodeURIComponent('\u00e9');
console.log(probe);
// Output: /search?q=%C3%A9
```

The final request produced the same backend behavior without triggering the firewall rule that had blocked every previous attempt. **The WAF had been normalized to expect decomposed Unicode, but I was sending composed Unicode.**
